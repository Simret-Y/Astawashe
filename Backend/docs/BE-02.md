# BE-02: Medication, Reminder & Adherence System

## Concepts and data model

- **Medication** is a reusable medicine catalog entry.
- **Prescription** assigns a medication, dosage, frequency, and date range to one patient.
- **Schedule** is a dose time under a prescription; a prescription can have any number of schedules.
- **Reminder** is one generated scheduled occurrence. `(schedule_id, scheduled_for)` is unique.
- **Notification** records an attempted PUSH, SMS, or VOICE delivery to a user.
- **Dose record** is the outcome of one expected occurrence. `(schedule_id, expected_at)` is unique.
- **Adherence** is an aggregate, not a stored table: `(TAKEN + LATE) / expected doses * 100`.
- **Guardian alert** is a guardian-specific missed-dose alert. One is allowed per guardian/dose/type.

The additive migration is `database/migrations/20260819_be02_medication_reminder.sql`. It never drops existing BE-01 data. `database/schema.sql` includes the same tables for a fresh local database bootstrap.

## Endpoints

All endpoints require `Authorization: Bearer <JWT>`.

| Method | Path | Description |
|---|---|---|
| POST/GET | `/api/medications` | Create/list medication catalog entries |
| GET/PUT/DELETE | `/api/medications/:id` | Read/update/delete a catalog entry |
| POST/GET | `/api/prescriptions` | Create/list authorized prescriptions |
| GET/PUT/DELETE | `/api/prescriptions/:id` | Read/update/cancel a prescription |
| POST/GET | `/api/schedules/prescriptions/:prescriptionId/schedules` | Add/list prescription schedules |
| PUT/DELETE | `/api/schedules/:id` | Update/deactivate a schedule |
| POST | `/api/reminders/process-due` | Admin scheduler bridge |
| GET | `/api/reminders` | List authorized reminders (`patient_id`, `status` optional) |
| GET/POST | `/api/reminders/:id`, `/api/reminders/:id/acknowledge` | Read/acknowledge reminder |
| GET | `/api/notifications`, `/api/notifications/:id` | Recipient's delivery history |
| POST | `/api/adherence/schedules/:scheduleId/take` | Mark expected dose taken or late |
| POST | `/api/adherence/schedules/:scheduleId/skip` | Mark expected dose skipped |
| POST | `/api/adherence/process-missed` | Admin missed-dose processor |
| GET | `/api/adherence` | Authorized adherence summary (`patient_id`, `start_date`, `end_date` optional) |
| GET/POST | `/api/guardian-alerts`, `/api/guardian-alerts/:id/read` | Guardian's own alerts/read action |

Example prescription request (admin only until professional assignment is available):

```json
{
  "patient_id": 7,
  "medication_id": 2,
  "dosage": "500 mg",
  "frequency": "3 times daily",
  "start_date": "2026-08-20",
  "schedules": [
    { "dose_time": "08:00", "dosage": "500 mg" },
    { "dose_time": "14:00", "dosage": "500 mg" },
    { "dose_time": "20:00", "dosage": "500 mg" }
  ]
}
```

Dose action requests require an exact occurrence:

```json
{ "expected_at": "2026-08-20T05:00:00.000Z", "notes": "Taken with food" }
```

## Permissions

- Patients read and act only on their own data.
- Guardians read only data for linked `patient_guardians` patients; alerts/notifications are limited to the guardian's own account.
- Medication catalog management is doctor, HEW, or admin.
- Admins manage prescriptions/schedules and run processing endpoints.
- BE-01 does **not** contain a healthcare-professional-to-patient assignment table. Therefore BE-02 deliberately does not grant doctors/HEWs patient-specific prescription access. Add an assignment relation before enabling that workflow.

## Processing flow

`processDueReminders(now)` is an idempotent scheduler-ready service. It scans active due schedules from the configurable `REMINDER_LOOKBACK_DAYS` window (default 2 days), inserts each reminder once, records a PUSH notification through the placeholder provider, and marks the reminder sent only after successful delivery. A cron worker or queue can later call this service without changing its callers.

`processMissedDoses(now)` scans the bounded `MISSED_DOSE_LOOKBACK_DAYS` window (default 2 days), creates/locks expected occurrences, transitions only `SCHEDULED` records to `MISSED` after `DOSE_LATE_GRACE_MINUTES` (default 60), then creates alerts and notification records for every linked guardian in one database transaction.

Dose transitions are terminal: `SCHEDULED → TAKEN`, `LATE`, `SKIPPED`, or `MISSED`. A repeat or conflicting action returns `409`.

## Notification abstraction

`notificationService.createAndSend` accepts `PUSH`, `SMS`, or `VOICE`, creates the notification audit row, and currently uses a controlled logging provider. It does not contain credentials or vendor SDKs. Later provider implementations can replace `sendWithLoggingProvider` while preserving the service interface and data model.

## Running and testing

1. Configure `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, and `JWT_SECRET` in `backend/.env`.
2. Apply the additive migration to the existing database, for example: `psql -d <database> -f database/migrations/20260819_be02_medication_reminder.sql`.
3. From `backend`, run `npm install`, then `npm start`.
4. Run the offline structural checks with `npm test`.

The included tests validate syntax, additive migration safety, required constraints, and route registration. Database-backed API tests require a configured PostgreSQL test database and valid JWTs; they are intentionally not run against an unknown shared database.
